# ADR: Sessions form an agent tree under personas

**Date:** 2026-09-03
**Author:** Raghav

## Context

Sprint 002 gave Bosun its own agent sessions: a per-session loop on the control plane, one executor process per session on the node, and a session-facing configuration of models and subagent types. A "subagent type" was `{ name, model, permission }`, and `spawn_subagent` ran a nested loop on the control plane inside the parent's turn: the parent blocked until the subagent finished, the subagent's events were written into the parent's transcript as `Block::Subagent` blocks, and a subagent could not hold a system prompt, a tool allowlist, or a transcript of its own. The tool surface that carried `spawn_subagent` is recorded in `2026-08-30-tool-surface.md`, and the session states it ran on in `2026-08-30-session-states.md`; both carry supersession notes pointing here.

Sprint 005 (`../sprints/005-agent-tree.md`) replaces that model. A persona is the unit of configuration, and a session may spawn child sessions under other personas: sessions form a tree of agents that communicate by authored messages. The tunnel the tree runs over changed with it and is recorded separately in `2026-09-03-one-tunnel-per-node.md`; this ADR records the decisions those notes point to.

## Decision Drivers

- One configuration unit must cover everything a role needs: model, system prompt, permission, and tool allowlist, plus a description a spawning agent can choose from.
- Delegation must not block the delegator: a child runs its own loop and executor concurrently with its parent and siblings.
- A parent needs the outcome of work it delegated, not the child's raw transcript, and must never lose track of children it spawned.
- Only questions no agent in the tree can resolve should reach the user, and an answer must reach the agent that asked, verbatim, without any intermediate model paraphrasing or relaying it.
- Interrupt and stop must mean the same thing across a tree, and a crash must lose no durable work.
- The system is single-user with no security model; the decisions below assume that and deliberately avoid authorization machinery.

## Options Considered

- **Subagents as nested loops on the control plane (sprint 002) vs. children as full sessions (chosen).** The nested loop ran inside the parent's turn, so a delegated task serialized the parent; it had no transcript of its own and surfaced as `Block::Subagent` transcript blocks. A child session runs its own loop and executor on the parent's node and working copy, stores its own transcript and model calls, and is a first-class row in `bosun list`, so siblings and parents are truly concurrent and each level supervises exactly like the root.
- **Subagent types `{ name, model, permission }` vs. personas (chosen).** A subagent type could not carry a system prompt or a tool allowlist, and permission was a session attribute the user set at `clone` time. A persona is `{ name, description, model, system_prompt, permission, allowed_tools }`; permission becomes persona-declared per session, so a read-only session is a read-only persona and `bosun clone --permission` disappears.
- **A tree-wide permission bound or a creation-time cap.** Rejected: single-user, no security; the model decides how many children to spawn and each child's surface is its persona's. A read-only root may spawn a read-write child when the child's persona declares it.
- **Children see the parent's transcript vs. communication by authored messages (chosen).** Transcripts couple every wake to the child's full history and leak the parent's reasoning. A child authors one event — report, ask, or failure — into its parent's thread; the parent's wake carries a manifest of live children instead of the children's transcripts.
- **The parent model resolves a surfaced question itself vs. mechanical routing in the control plane (chosen).** A model-mediated answer path would need the root model to know the origin leaf and would paraphrase the question on its way down. Routing is mechanical: the user's answer is appended to the origin leaf's own session row and that leaf's loop is woken, and no intermediate model ever handles the answer. The root model only ever sees its own direct child.
- **A pending-ask binding keyed by the origin leaf vs. keyed by the direct raised child with the origin leaf carried on the row (chosen).** The binding names the session the raiser can actually message — the direct child the surfaced Ask block names — so a `message_child` cancel clears the row and the child's next authored event proves the question closed, at every level of the tree. The origin leaf is the routing target a user's answer is appended to and stays internal to the binding, out of every model's view.
- **A whole-tree interrupt on one press vs. an interrupt ladder (chosen).** Stopping children that are still doing useful work just because the root is mid-flight loses work for no reason. The first interrupt stops the root's own session; once the root is parked, the next stops the rest of the tree. The ladder derives from the root's own state, so it needs no extra bookkeeping.
- **Crash-interrupted sessions holding until the user acts (session-states ADR) vs. crash-interrupted children reporting to their parent (chosen).** A child has no user of its own, so "hold until the user acts" would leave crashed children stopped forever; instead the child authors a failure event and the parent re-decides it. This relaxes `2026-08-30-session-states.md` for the crash cause only; user-interrupted sessions still hold until the user acts.
- **Injecting the repo-standard files' contents into context vs. a presence notice with on-demand reads (chosen).** Contents never leave the node over the presence call and never enter stored messages; each session is told the standards exist and reads them with the file tools when its task needs them. Persona prompts stay purely about role and behaviour.
- **One tunnel per session vs. one tunnel per node.** Recorded in `2026-09-03-one-tunnel-per-node.md`; a session tree is exactly the case that made one-per-session multiply connections.

## Decision

**Personas replace the session-facing model and subagent configuration.** `ControlConfig` carries `personas`, a map of `PersonaConfig` by name, and `default_persona`, which names what sessions use when a request gives none. A `PersonaConfig` is `model` (naming a configured provider entry), `permission`, `allowed_tools` (a canonical tool list or `"*"`, which is the default), `description`, and a system prompt body read from `<data dir>/personas/<name>.md` when the file exists; a persona without a prompt file keeps no system prompt and falls back to the loop's default system text. Boot validates that every persona's model is configured, its tool names are canonical, and `default_persona` names a persona. `bosun clone` and `bosun dev` take `--persona` instead of `--model` and `--permission`. Personas resolve live by name at session start and at spawn: an unknown persona is a clear error — a root request fails at session start, a spawn returns the error to the spawning parent.

**Permission is per-session and persona-declared, with no tree-wide bound and no creation-time cap.** A session's stored permission and `allowed_tools` come from the persona it was created under. The session's own executor enforces the persona's permission (read-only refuses shell, `file/write`, and `edit` regardless); the allowlist is applied control-plane-side per turn when the tool schema is built. A read-only root may spawn a read-write child when the child's persona declares it.

**A persona switch on the root is a full live swap.** `POST /sessions/{id}/persona`, root sessions only, replaces the stored persona, model, permission, and allowed-tool spec in one store transaction and records a durable persona event on the session's stream. The loop re-resolves the session at every turn, so the new model and system prompt apply from the next model call; a turn in flight is not aborted. When the permission changes, the executor's permission toggles live through the existing `/permission` path, best-effort like `set_permission`; the store is authoritative. Running children are unaffected, each keeping its own persona; children are watch-only and never switch by user action.

**A subagent is a full session; sessions form a tree.** Every session carries `parent_id` (the session that spawned it; none for a root) and `owner_id` (the tree root; a root owns itself), stored on the `sessions` row alongside `persona`, `allowed_tools`, and `interrupt_cause`. `model` is resolved from the persona at creation. `spawn(persona, instructions)` creates a child session on its parent's node and working copy: the node starts the child's own executor on the parent's directory, the control plane creates the child's row born `creating` with the instructions as its first prompt, and the child's own loop starts; the tool returns the child's id and the parent's turn continues without waiting. The recursion is unlimited: any session whose persona's surface includes `spawn` may spawn children and supervises them exactly as the root does, one level down, and the persona catalog is advertised to spawn-capable sessions as name plus description, never as prompt text.

**Communication between parent and child is authored messages, never transcripts.** A child reports by ending its turn without an ask: it authors a completion report to its parent and sets itself `stopped`. A child that asked a question authors an Ask event and waits; a child whose turn failed authors a failure event. The authored event is a `Block::ChildEvent` appended to the parent's thread — `child_id`, `event_kind` (`report`, `ask`, or `failure`), `text`, and for asks the mechanically stamped `origin` leaf — and appending it wakes the parent's loop. Events that land mid-turn queue until the turn ends, and each wake's turns read the thread as it stood when the wake began plus the wake's own tool traffic, so an event that lands mid-wake is invisible to the running wake and surfaces only in its own queued wake. Each wake carries a manifest of live children — id, persona, state, and last authored message — in the system prompt: a child is live while it can still act, or while its latest authored event has not been surfaced by a completed wake yet, and it leaves the manifest once its completion is handled and not resumed. A parent asks a child for detail or redirects it with `message_child(id, text)`, which appends the message to the child's thread and wakes the child's loop; a stopped or interrupted child resumes from its archived thread and reports again. A session that spawned supervises: it does not report to its parent until nothing it spawned can still act or holds an unhandled event, so a mid-tree session that delegated waits for its subtree like a root waits for the user.

**Ask gating is hierarchical.** `ask` is contextual: at the root it reaches the user; at a child it raises the question to that child's parent, which answers on the user's behalf when confident, denies with a reason, or surfaces the question upward. A surfaced question binds to its origin leaf and is recorded in a durable `pending_asks` row: the raising session, the direct child whose question it raised, that question's origin leaf, the surfaced question, and the surfaced Ask block's message id. The row names the direct child at every level — the session the raiser can actually message — so a `message_child` to it cancels the ask and clears the row, and the child's next authored event proves its question closed and clears the row too. One question is raised at a time at every level: a session with a row pending refuses a further `ask` until its raised child authors its next event or the session cancels it with `message_child`. The user's answer routes mechanically and verbatim to the origin leaf's own session row and loop: the control plane appends the answer to the leaf and wakes it, and the root model is never involved. An answer with no pending binding, or whose origin leaf is gone, is an ordinary root message, and the stale binding is cleared. When the user redirects instead of answering, the root model wakes with the surfaced ask still in its thread and decides — it can answer or cancel by messaging the direct child its surfaced ask names, which clears the row, so a redirect cannot deadlock the root into silence. The surfaced Ask block names that same direct child, never the leaf: the root's model only ever needs to know its own child.

**Lifecycle.** The interrupt ladder is root-only. The first interrupt stops the root's own session; once the root has nothing in flight, the next interrupt stops every other session in its tree. The cause of an interrupt is recorded on the session as `interrupt_cause` (`User` or `Crash`) when the session becomes interrupted and kept while it stays stopped. User-interrupted sessions hold until the user acts: no wake starts a turn in them except the user's own message or a parent's `message_child`. Crash-interrupted children report a failure event to their parent — on a control-plane restart after boot recovery, or when their own turn fails — and the parent re-decides each one: resume it with `message_child`, abandon it, or swap it to another persona. `bosun stop` on the owner cascades the whole tree; on a child it cascades that child's subtree. Teardown runs leaves-first: each stopped session's executor is torn down on its node, its loop task is dropped, and its rows are removed, so a stopped subtree is gone while the node's tunnel stays. A completed child's session state is `stopped`; completed-versus-failed-versus-user-stopped is distinguished by the final authored event (report, failure, or none), not by the state, and a stopped child keeps its loop task and executor so a parent's `message_child` can resume it.

**Tool surface.** The canonical list drops `spawn_subagent` and gains `spawn(persona, instructions)` and `message_child(id, text)`. `ask` is contextual as above; `todowrite` is root-only twice over — children never see it in the schema and a call from a child is refused. Advertisement is decided by what is attached, not by depth: `spawn` shows only when personas are configured and a spawner is attached, `message_child` only when a mailbox is attached, and every other tool is available to any session whose persona allows it. Read-only sessions drop the mutating tools as before.

**Transport.** One tunnel per node, with session-addressed logical connections to each session's executor, as recorded in `2026-09-03-one-tunnel-per-node.md`; that ADR supersedes the one-tunnel-per-session sections of `2026-08-21-nodes-dial-out-only.md` and `2026-08-30-tool-protocol-over-tunnel.md`, and this one does not restate it.

**Repo standards.** The loop scans the working copy for the repo's governing documents and injects a presence notice, never contents. The executor answers an internal `repo_standards` presence call listing which of `AGENTS.md` and `CLAUDE.md` exist at the working-copy root, in that order; the loop fetches it once per session, caches it, and composes each turn's system prompt from the presence list alone. The contents are never fetched by the loop and never enter stored messages; an agent reads them with the file tools when its task needs them.

**States and store.** The five session states of `2026-08-30-session-states.md` are reused unchanged. `model_calls` stay per session; cost rolls up by `owner_id` when the deferred cost views arrive.

This supersedes the sprint-002 subagent model (`../sprints/002-agent-executor.md`, S8: subagent types `{ name, model, permission }` and the `spawn_subagent` tool) and the tool-surface part of `2026-08-30-tool-surface.md` that carried `spawn_subagent`; both earlier files carry supersession notes. It relaxes `2026-08-30-session-states.md` for the crash cause only, as that ADR's note records.

## Consequences

- Delegation composes and runs concurrently: a parent continues while children work, each level supervises its own children, and every child is a first-class session with its own transcript, model calls, and state.
- One working copy is shared by a whole tree. Concurrent children can edit the same files; there is no isolation between sessions on a node, which the single-user scope accepts.
- A live tree holds one executor process per running or stopped-but-resumable session on the node, so a long-lived tree accumulates processes until the owner is stopped; `stop` then removes the whole subtree leaves-first.
- Watch-only children mean the user cannot steer a child directly: every instruction to a child goes through the root model and `message_child`, and a message to a supervising child yields no report until its whole subtree resolves.
- The per-wake manifest is built by scanning the parent's full archived thread for each child's last authored message — cheap while transcripts are small.
- A surfaced ask serializes a level: one pending ask at a time per session, and a waiting parent cannot raise again until its raised child answers or is cancelled.
- Stored transcripts holding `{"kind":"subagent",...}` blocks (written by the sprint-002 `spawn_subagent` era) or `{"kind":"child_report",...}` blocks (written by the first build that spawned real children) stop deserializing once those block shapes are gone; there is no migration, which pre-1.0 dev data accepts. Newer fields on `Ask` and `ChildEvent` serialize only when set, so the older transcript shapes they extend still parse.
- A control-plane crash between a child appending its event and the parent's loop being woken loses the ephemeral wake; the event is durable in the parent's thread and surfaces on the parent's next wake, so the loss is a delay, not data loss.
- A control-plane crash between the node starting a child's executor and the child's row existing can orphan an executor on the node.

## Revisit When

- A real authorization model appears: tree-wide bounds, creation-time caps, or an escalation or approval channel.
- A user must message or steer a child directly, or a session must interact outside its own lineage.
- The per-wake manifest scan over the full archived thread becomes a measurable cost; a per-child lookup of the last authored message would replace it.
- Ask gating needs more than one pending ask per level, or an answer must be reviewed by an intermediate model rather than routed verbatim to the leaf.
- Interrupts need finer granularity than root-then-rest — for example a subtree interrupt aimed at one child.
- Repo-standard contents must reach context without the agent reading the files, or presence must be re-scanned mid-session.
